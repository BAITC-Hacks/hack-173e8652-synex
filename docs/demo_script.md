# Демо-сценарий на 5 минут

## Подготовка до выступления

Из корня проекта:

```bash
source .venv/bin/activate
make analyze
python scripts/verify_outputs.py --out ./out --expected-nodes 2248
make dev
```

Открыть:

- UI: `http://127.0.0.1:8501`;
- Swagger: `http://127.0.0.1:8000/docs`;
- health: `http://127.0.0.1:8000/health`.

Не выбирать `gid` заранее в коде. Для стабильного demo взять первую строку фактически сформированного `out/top_nodes.csv`, а для common receivers — два или несколько seed из UI/данных.

## 0:00–0:35 — проблема и ценность

**Фраза:** «У аналитика есть 2 248 обезличенных клиентов и тысячи переводов, но нет ground truth и нельзя вручную просмотреть весь граф. MoneyGraph отвечает не “кто виноват”, а “кого проверить первым, почему и какой следующий шаг нужен”».

Показать Dashboard: counts, период, компоненты, распределение ролей и предупреждения качества данных.

## 0:35–1:05 — воспроизводимый запуск и validation

Показать команду:

```bash
python -m moneygraph.cli analyze --data ./data --out ./out
```

Открыть validation summary. Подчеркнуть:

- edges сверены с агрегированными transactions;
- все узлы, включая изолированные, сохранены;
- исходные Parquet не исправляются молча;
- run manifest содержит input hashes и длительности этапов;
- AI не участвует в обязательном pipeline.

## 1:05–1:45 — top node и объяснимость

Открыть Top Nodes и выбрать первую строку текущего результата.

Показать последовательно:

1. роль и `role_score`;
2. `priority_score` как приоритет проверки, не вероятность нарушения;
3. числовой evidence;
4. вклад драйверов priority;
5. ограничения seed/depth 4, если применимы.

**Ключевая фраза:** «Каждый балл раскладывается на наблюдаемые признаки; нет скрытой LLM-классификации».

## 1:45–2:25 — граф и трассировка

Перейти в Network Explorer по выбранному `gid`:

- показать направленный ego graph на одно колено;
- увеличить до двух колен;
- на ребре показать сумму и число операций;
- выполнить downstream или upstream trace;
- обратить внимание на bounded depth/path limits.

Если выбранный узел находится на depth 4 без выхода, специально показать предупреждение: отсутствие исходящих в выгрузке не подтверждает terminal.

## 2:25–3:00 — common receivers

В Flow Investigation выбрать несколько `gid`, запустить Common Receivers.

Показать для первого кандидата:

- coverage выбранных источников;
- min/avg distance;
- примеры путей;
- наблюдаемый поток;
- собственные role/priority кандидата.

**Фраза:** «Это детерминированный графовый поиск. Copilot может объяснить результат, но не создаёт его».

## 3:00–3:30 — кластеры и resilience

Открыть Clusters: размер, seed, внутренний оборот, top gids и осторожную offline-гипотезу. Затем показать resilience для удаления top-N и низкоприоритетного baseline.

Не говорить, что граф “обязательно разрушится”: это структурный сценарий для наблюдаемой выборки.

## 3:30–4:05 — investigation workflow

Создать case из выбранного узла:

1. задать название;
2. добавить один-два узла;
3. оставить заметку с рекомендуемой проверкой;
4. изменить статус на `in_review`;
5. экспортировать JSON или CSV.

Показать audit events. Уточнить, что demo analyst — метка аудита, а не фиктивная банковская авторизация.

## 4:05–4:30 — Copilot/fallback

С выключенным AI задать: «Почему этот узел в топе?» Показать deterministic fallback с реальными `gid` и метриками.

Если утверждённый ключ настроен локально, можно включить provider; обязательный результат не должен меняться. Не показывать `.env`, ключи или полный raw context.

## 4:30–5:00 — итог и масштабирование

**Финал:**

- ценность: сокращение пространства ручной проверки до объяснимого приоритетного списка;
- качество: единый путь Parquet → validation → roles/priority → graph → case export;
- инновация: observation-aware scoring, который не путает depth 4 и seed bias с поведением клиента;
- развитие: сменяемый graph engine, feature store, DWH ingestion, PostgreSQL, IAM/SIEM;
- честная граница: pilot-ready reference implementation, не промышленная сертификация.

## Ответы на вероятные вопросы жюри

### «Почему это не просто PageRank?»

PageRank — один из драйверов. Роли различают сбор, распределение, быстрый транзит, структурный мост и вероятный terminal; используются направления, суммы, counts, время, seed reach и cluster bridges.

### «Как вы знаете, что узел подозрительный?»

Не знаем и не утверждаем. Система формирует приоритет проверки и показывает причины. Для вывода нужны дополнительные банковские данные и регламент аналитика.

### «Почему не AI end-to-end?»

Обязательные scores должны быть воспроизводимы, проверяемы и работать offline. AI полезен как интерфейс объяснения и навигации, но не как непрозрачный источник решения.

### «Как учтена неполнота графа?»

Для seed отключена валидность простого pass-through; для depth 4 ограничен terminal score. Ограничения входят в evidence и следующий шаг проверки.

### «Что произойдёт на миллионе узлов?»

Формулы и контракты сохраняются, NetworkX заменяется на igraph/graph-tool либо распределённый движок; batch отделяется от online serving, вводятся incremental features, feature store, queue и bounded graph cache.
