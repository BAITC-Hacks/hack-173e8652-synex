# Agentic AML Loop — демо на 5 минут

## Подготовка до выступления

Из корня проекта:

```bash
source .venv/bin/activate
make analyze
python scripts/verify_outputs.py --out ./out --expected-nodes 2248
make dev
```

Открыть:

- UI: `http://127.0.0.1:8501`;
- Swagger: `http://127.0.0.1:8000/docs`;
- health: `http://127.0.0.1:8000/health`.

В UI выбрать раздел `Agentic Loop`. Не заучивать `gid` и число alerts: запускать replay и показывать фактический результат. До выступления один раз выполнить `./scripts/smoke_test.sh`; скрипт использует временную БД и не засоряет demo-state.

## 0:00–0:35 — проблема и обещание продукта

**Фраза:** «AML-аналитику не нужен ещё один граф из тысяч точек. Ему нужен управляемый цикл: система замечает наблюдаемый сигнал, объясняет его, предлагает следующие шаги, а человек решает, что разрешить».

Показать четыре вкладки:

1. `Мониторинг`;
2. `Alert + Explain`;
3. `Decision Support`;
4. `Approve → Execute → Audit`.

**Ключевая формулировка:** «ИИ — второй пилот, не автопилот. Финальное решение и ответственность всегда у аналитика».

## 0:35–1:20 — 1. Проактивный мониторинг

На вкладке `Мониторинг` выбрать доступную дату и запустить scan.

Сразу указать честную границу:

- это симуляция последовательного поступления данных по календарным дням, а не realtime-stream;
- scan в pilot запускается кнопкой; interval показывает будущую cadence, фонового scheduler здесь нет;
- исходник содержит дату, но не внутридневное время;
- поэтому система не заявляет `dwell < 2 часов`, а проверяет наблюдаемое перенаправление за 0–2 дня.

Показать, что детерминированные правила проверяют наблюдаемые признаки:

- не менее восьми уникальных плательщиков за день;
- дневной входящий объём больше 1 000 000 KZT;
- pass-through в диапазоне 0.9–1.1 вместе с быстрым перенаправлением за 0–2 дня.

Выбрать alert из фактически полученной ленты. Не говорить «найден преступник»: это сигнал для проверки.

## 1:20–2:05 — 2. Alert + Explain

На вкладке `Alert + Explain` показать карточку выбранного узла:

- какие правила сработали;
- конкретные наблюдаемые метрики;
- роль, кластер и приоритет аналитической проверки;
- ограничения полноты выборки и дневной гранулярности;
- какие дополнительные данные нужно запросить.

**Фраза:** «Alert воспроизводим: LLM не придумывает факт и не меняет score. Он может только объяснить уже рассчитанные признаки».

Уточнить: `priority_score` и `recommendation_score` — ранжирование проверки и полезности следующего шага, а не вероятность нарушения закона.

## 2:05–2:55 — 3. Три безопасных решения

На вкладке `Decision Support` запросить предложения и показать ровно три server-owned варианта:

1. подготовить локальный AML-review draft;
2. построить ограниченный маршрут движения денег;
3. создать локальный watchlist связанных узлов.

Для каждого показать обоснование, ожидаемый результат и `recommendation_score`.

**Фраза:** «Модель не может подменить инструмент или добавить команду “заблокировать”. Разрешённые действия задаёт сервер, а не текст LLM».

## 2:55–4:10 — 4. Человек решает, система исполняет

На вкладке `Approve → Execute → Audit` показать оба пути.

Сначала выбрать один вариант и нажать `Reject`. Показать, что решение записано, но инструмент не запускался и побочного эффекта нет.

Затем выбрать другой предложенный вариант:

1. отметить явное подтверждение;
2. ввести `APPROVE`;
3. нажать исполнение;
4. показать локальный результат: draft, bounded route или watchlist — в зависимости от выбранного действия.

Обязательно проговорить:

- система не блокирует счёт, клиента или перевод;
- draft остаётся локальным и никуда не отправляется;
- повтор с тем же idempotency key не должен дублировать результат;
- аргументы инструмента берутся из сохранённого предложения, а не из произвольного текста пользователя.

## 4:10–4:40 — полный audit trail

В этой же вкладке открыть журнал и провести по цепочке:

```text
scan → alert → proposals → analyst reject/approve → execution result
```

Показать actor, entity, transition и время. Уточнить: `ANALYST_NAME` — demo-метка, не банковская аутентификация; SQLite-аудит проверяем в демо, но он не является промышленным WORM/SIEM-хранилищем.

## 4:40–5:00 — финал

**Финальная фраза:**

«Мы реализовали Human-in-the-Loop, обязательный для ответственного AML-процесса. Система проактивно выявляет и ранжирует наблюдаемые сигналы, готовит объяснение и безопасные действия, но решение всегда принимает аналитик. ИИ — второй пилот, не автопилот: недели ручной трассировки превращаются в проверяемую гипотезу и контролируемое действие за один рабочий цикл».

Связать с критериями:

- ценность — быстрее перейти от массива переводов к проверяемому следующему шагу;
- качество — полный workflow от scan до audit receipt;
- инновационность — graph + temporal signals + constrained agentic execution;
- масштабирование — заменить replay на поток и SQLite на корпоративное хранилище, сохранив контракты и human gate;
- демо — весь цикл исполняется в UI, а не изображается слайдами.

## Резервный сценарий

Если Streamlit недоступен, показать Swagger и запустить:

```bash
./scripts/smoke_test.sh
```

Smoke поднимает API и UI на loopback, выполняет базовые проверки и Agentic flow: scan → proposals → reject → approve с `APPROVE` и idempotency key → audit.

Для полной локальной проверки:

```bash
make verify
```

## Ответы на вероятные вопросы жюри

### «Это настоящий realtime?»

Нет. В кейсе только календарные даты, поэтому UI честно показывает batch replay по дням. Промышленный streaming — следующий адаптер ingestion; текущая демонстрация проверяет логику и workflow без выдуманной часовой точности.

### «Почему AI сам не блокирует счёт?»

Потому что alert — гипотеза, а ограничительное или регуляторное действие требует полномочий, контекста и ответственности человека. В пилоте нет инструментов блокировки, заморозки или внешней отправки.

### «Что именно здесь agentic?»

В демо аналитик инициирует scan, после чего сервис детерминированно проверяет окно, собирает alert-контекст, формирует ограниченный набор действий и только после явного решения вызывает разрешённый инструмент. Главное отличие — управляемый loop с состояниями, idempotency и аудитом, а не свободный чат; production scheduler остаётся интеграционным шагом.

### «Почему доверять объяснению?»

Факты и trigger codes приходят из rules/graph engine. LLM не назначает роли, не меняет scores и не создаёт новые tool keys. Без ключа весь обязательный сценарий работает на детерминированном fallback.

### «Recommendation score — вероятность отмывания?»

Нет. Это поддержка конкретного следующего шага наблюдаемыми признаками. Без ground truth система не заявляет вероятность нарушения.

### «Как масштабировать?»

Контракты scan/alert/proposal/decision/audit сохраняются. Для банка batch replay заменяется event ingestion, NetworkX — масштабируемым graph engine, SQLite — PostgreSQL и WORM/SIEM, demo actor — SSO/RBAC с maker-checker.
